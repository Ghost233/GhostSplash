# MoE 专家缓存随系统内存压力伸缩的设计讨论

状态：历史访谈记录。2026-10-27 用户将当前范围改为单实例，以下 Q10、Q13～Q15 的跨实例决策已取消。
Q16 的恢复节流改为当前实例内生效。本文仅供追溯，实施以[当前规格](specs/moe-shared-memory-manager.md)和 [ADR 0005](adr/0005-single-instance-memory-control.md) 为准。

## 已明确的需求

- 适用于不同的受支持 MoE 模型，包含没有 PLE 的模型。
- 用户可以给定全局预算，专家缓存容量在该预算内调整。
- 从真实模型与量化格式计算容量，10 GiB 和特定型号均只是此前的示例。
- 系统内存使用百分比不能直接换算成专家缓存比例。
- 保留模型执行所需的存储下限，并区分容量、实际驻留量和命中率。

## 当前代码事实

- `runtime/main.mm` 的 `MemoryPressureMonitor` 已接入系统压力事件，并设置 500 ms 的检查定时器。
- `runtime/model/ModelSizing.cpp` 从权重格式计算专家全量大小和最小存储预算。
- `runtime/model/ExpertStore.hpp` 提供缓存调整接口，要求调整时没有 GPU 命令在执行。
- 可调整的专家存储布局本身不依赖 PLE。当前运行时通过 `expertPleAdaptive` 启用它，仍与专家和 PLE 同时存在的条件耦合。
- 普通全驻留权重不能直接调用缓存调整接口。可调整存储必须在构造时启用，并在 GPU 安全点停止相关预读后释放存储块。
- 当前 `ExpertPlePolicy` 保持总池大小不变。系统压力升高时，这个策略暂停比例调整。
- 分配足够容纳全部专家的缓存容量，不代表启动时已经将全部专家读入缓存。
- 存储按块调整，需保留各尺寸组的执行下限。调整失败可能已释放部分存储，必须依据实际分配核对记账。
- 现有空闲恢复会申请专家存储释放前的容量，尚未按当前系统余量重新选容量。PLE 当前不随专家权重一起空闲释放，恢复规划需计入它仍保留的实际分配。

这些事实只说明现状和约束，不等同于已选定新方案。

## 设计树

第一轮已确认：

- Q1：专家占比采用权重字节容量比例。辅助开销、实际驻留比例和命中率分别报告。
- Q2：系统响应优先于推理吞吐量，允许通过缩小专家缓存让出内存。持续 Warning 不强制要求恢复到 Normal，仍需依据余量和换页趋势决定缩容。
- Q3：新功能独立开关，默认关闭。开启后只调整 auto 专家预算，手动预算保留固定语义。

第二轮已确认：

- Q4：系统预留余量提供 auto 和手动大小两种方式。auto 复用现有主机保护规则，展示计算结果；手动值明确设定保护余量，不视为系统保证的可用字节数。
- Q5：专家缓存降到模型下限仍不足时，暂停新请求的启动，让已接纳请求等待恢复。超过现有资源等待期限后，向受影响请求报资源不足。内存保护本身不直接退出服务，也不自动降低上下文或量化精度。
- Q6：同一压力控制器管理 auto 专家和 auto PLE 的可用总预算。现有配额策略只在该预算内调整比例。手动 PLE 配额保持固定；没有 PLE 的模型只调整专家。

第三轮已确认：

- Q7：Warning 时依据系统预留余量缺口按实际存储块缩容，每轮核对释放效果，再决定是否继续。余量足够时保持容量并暂停扩容。Critical 时尝试将自动存储缩到模型允许的下限，仍不足则进入 Q5 的等待流程。
- Q8：系统恢复 Normal、满足现有恢复余量门槛，并连续稳定 30 秒后才扩容。每 5 秒最多增加一个实际存储块，再次警告或增长失败就停止增长，重新开始稳定观察。这些时间是首版待验证的策略值，不是系统提供的安全保证。
- Q9：压力缩容释放的额度暂不追加给 KV 和状态缓存的扩容上限。用户全局上限保持不变，正在服务的请求继续遵守原有资源保护规则。

第四轮已确认或调整：

- Q10：用户要求共享 manager，由参与实例动态选举产生；不单独启动 manager 进程。原先各进程独立分配的首版建议不采用。
- Q11：空闲释放后，在恢复专家存储前依据当前余量、仍保留的 PLE 分配和模型下限选容量，避免先恢复旧的大容量再缩容。不足时按 Q5 等待。
- Q12：先完成压力状态注入、分配失败与完整正确性检查，再单独安排性能测试。不通过填满整机内存制造真实压力。覆盖默认关闭、手动配额保护、无 PLE 与有 PLE 的模型、实际释放、状态一致性、缩扩容和恢复。

第五轮已确认：

- Q13：同一台 Mac、同一系统用户、跨模型和仓库使用一个协调组；独立用户及未加入的程序作为外部负载。系统基础预留只计一次，多个实例要求不同时取较大值。
- Q14：协调者崩溃后自动选举。失联时冻结新增长，保留本地缩容和已分配资源上的推理；只有获得唯一领导锁才接任，存活但卡住且持有领导锁时不因心跳超时强抢。
- Q15：先保证正在服务实例的最低需求，优先回收空闲实例的可选缓存，再向活跃实例均分额外缓存字节。达到某实例上限后，剩余额度再分给其他实例，各模型占比可以不同。

2026-10-26 补充确认：

- Q16：冷启动先分配模型执行下限。系统 Normal、达到恢复余量门槛并连续稳定 30 秒后，协调组每 5 秒最多增加 1 个实际存储块，逐步增长到上限允许的全容量。达到全容量后仍保留可缩容布局；全容量不代表所有专家已预热驻留。
